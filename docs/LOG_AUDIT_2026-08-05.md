### C-3 — Der Brain-Embedding-Cache hat keinen Schreiber; die Live-DB ist leer

**Symptom:** 571 Warnungen `No exact video embedding for hash … and model siglip_vision@onnx-dml-v1`
(563 distinkte Hashes) — obwohl im selben Lauf 349 SigLIP-Embeddings „gespeichert" und 58 „wiederverwendet"

```
C:\Users\david\AppData\Roaming\PB_Studio\brain\embedding_cache.db
  SELECT COUNT(*) FROM media_embedding_index   ->  0
  ...\brain\embeddings\                        ->  0 Dateien     (seit Anlage 31.05. leer)
```

Beide Seiten benutzen **denselben** Hash (sha256 über Dateiinhalt, `src/pb_studio/core/media_hash.py:20-50`) —
der Bruch liegt eine Ebene höher: `_commit_pending_video_embedding` (`backend/routers/video_router.py:231-247`)

  Genau deshalb wirken die Confidence-Werte unauffällig.
- `semantic_match_weight` bekommt **nie** einen Bridge-Wert → nie ein Feedback-Event →
  `weight_store` bleibt permanent unter `MIN_CONFIDENT_SAMPLES=10` → ewiger Cold-Start-Prior 0.5.
  **Die einzige Achse, die Audio↔Video-Semantik überhaupt bewertet, ist dauerhaft tot.**
- `projector_trainer.py:75-77` lädt Trainingspaare über dieselben Lookups → `collect_training_pairs`
  liefert immer leer → `W_audio`/`W_video` bleiben für immer die zufälligen
  Johnson-Lindenstrauss-Matrizen aus `_init_random_matrices`.

**Nutzersichtbar:** Die Regie schlägt Clips vor, die rhythmisch/Motion/Helligkeit passen, aber
**thematisch beliebig** sind — kein „dunkler Drop → dunkler Clip". Das deckt sich exakt mit
„Brain lernt nicht / schlägt Unsinn vor".

**Kein Dimension-Mismatch:** `cross_modal_projector.py:39-46` zieht `DEFAULT_AUDIO_DIM=512` /

**Fix:**

   projektgebunden über `media_id`, der Brain-Cache bewusst cross-project über den Hash.
2. Audio-Producer bauen (→ H-5).
3. **Backfill:** die 898 Vektoren in `video_index` enthalten Vektor + `video_hash` in den Metadaten —
   ein einmaliges Migrationsskript füllt den Brain-Cache, **ohne 563 Clips neu zu analysieren**.
4. Erst **danach** über Cold-Start/`weight_store` für `semantic_match_weight` reden — vorher ist
   jede Aussage über diese Achse bedeutungslos.

## 2. HIGH

### H-0 — Die Stem-Regler sind faktisch wirkungslos

**Symptom:** 42.188 Stem-Trigger (27.337 Drum + 14.851 Bass), 12 s Rechenzeit → **netto −18 Cuts**
(2595 → 2577).

**Root-Cause — Sättigung + Replace-statt-Add:**
```
advanced_pacing_engine.py:1550  base_cuts = self._generate_cut_list_from_audio(..., min_cut_interval*2)
advanced_pacing_engine.py:1583  all_triggers = base_cuts + stem_triggers
advanced_pacing_engine.py:1586  filtered = self._enforce_minimum_interval(all_triggers, min_cut_interval)
advanced_pacing_engine.py:1598  filtered = self._enforce_clip_lengths(..., min_length=ts.min_clip_length, ...)
```
`_enforce_minimum_interval` (`:2056-2076`) ist ein **Replace-statt-Add-Greedy**:
```python
if trigger.time - last_time >= min_interval:
    filtered.append(trigger); last_time = trigger.time
elif trigger.strength > filtered[-1].strength:
    filtered[-1] = trigger          # ERSETZEN, nicht hinzufügen
    last_time = trigger.time
```
Die Cut-Anzahl ist bereits durch `min_clip_length` **gesättigt**, bevor Stems überhaupt ins Spiel kommen:
Basis 2595/3299,5 s = **1,272 s**, final 2577/3299,5 s = **1,280 s** — beide auf demselben Boden.
Schon die Basis (6530 Beats + Onset + Energy) liefert weit mehr Kandidaten als `duration / min_clip_length`
zulässt. **42.188 zusätzliche Kandidaten können prinzipiell keinen einzigen Cut hinzufügen** — nur über den
`elif`-Zweig Zeitpunkte verschieben.

**Warum sogar −18:** der `elif`-Zweig setzt `last_time` auf den *späteren* Ersetzer (`:2074`). Jede Ersetzung
schiebt das Fenster nach vorn und verschluckt dadurch einen nachfolgenden legalen Slot.

**Strukturell inkonsistent:** Basis-Cuts entstehen mit `min_cut_interval*2` (`:1553`), die Merge-Stufe nutzt
`min_cut_interval` (`:1586`) — offensichtlich in der Absicht, Stems in die Lücken zu setzen. Diese Absicht
kassiert die finale `min_clip_length`-Stufe (`:1598`) wieder. Zusätzlich läuft `_enforce_clip_lengths`
**doppelt** (`:1199` und `:1598`).

**Fix:** entweder (a) Basis-Cuts ohne `_enforce_clip_lengths` erzeugen und die Längenerzwingung genau einmal
am Ende laufen lassen, **oder** (b) — besser — Stem-Trigger als **Stärke-Boost auf existierende
Basis-Trigger** (Zeitfenster-Match) einspeisen statt als zusätzliche Kandidaten. Option (b) macht die Regler
tatsächlich hörbar wirksam. Zusätzlich: `_enforce_minimum_interval` darf `last_time` beim reinen Ersetzen
nicht nach vorn schieben.

**Trigger-Zahlen selbst sind plausibel, kein Rausch-Threshold:** Bass 4,50/s ≈ exakt Achtelnoten bei 139,7 BPM;
Drums 8,28/s sind die **Summe dreier** Detektorläufe (kick/snare/hihat) — ein 16tel-Hihat allein wäre 9,31/s.
Eher konservativ als zu empfindlich.

### H-5 — CLAP-Audio-Embeddings haben keinen Producer

`src/pb_studio/brain/post_processor.py:259-277` (`_load_audio_embedding`) macht ausschließlich einen
**Cache-Lookup**, nie eine On-Demand-Berechnung. `src/pb_studio/audio/audio_embedder.py:78` (`embed_audio`)

`cache.store(media_type="audio", ...)` kommt **ausschließlich in `Tests/`** vor (13 Treffer), **0× in `src/` oder `backend/`**.

**Folge:** Der Cache ist strukturell leer → die Cross-Modal-Achse Audio↔Video (`bridge_dimensions.py:133`)
fällt permanent auf `partial` / `audio_embedding_missing_or_invalid` (`feature_adapter.py:300`) zurück.
Die 600 MB VRAM für die CLAP-Encoder sind für die Brain-Achse **verschwendet** — nur die Mood-Klassifikation
in `smart_director` nutzt sie.

**Offene Fachfrage vor der Implementierung:** Liefert `encode_audio` bei einem 60-min-DJ-Mix ein sinnvolles
Mix-Level-Embedding? `audio_embedder.py:26-29` dokumentiert Window/Hop 10 s/5 s + Mean-Pooling als
Soll-Aggregation, `clap_wrapper.py:238-240` macht aber nur ein naives `np.mean` über die Achse.

Zusätzlich: `models/clap_combined.onnx` ist in der Registry registriert, **existiert aber nicht**
(einziger ERROR der aktuellen Session, 00:39:15). `clap_wrapper.py:101` probiert es als bevorzugten
Single-Session-Pfad; `model_loader.py:343-349` loggt bei fehlender Datei `logger.error` und gibt `None`
zurück (kein Raise), `:108-118` fällt sauber auf `clap_audio` + `clap_text` zurück und setzt
`_classification_available = True`. `encode_audio`/`encode_text` nutzen `combined_session or audio_encoder_session`
